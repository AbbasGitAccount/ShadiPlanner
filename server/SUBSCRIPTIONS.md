# Subscription configuration and payment handoff

`npm run build` then `node scripts/test-subscriptions.mjs` runs concurrency and API checks in a temporary PostgreSQL schema. The script creates and removes only that isolated schema; it does not change real accounts.

The startup migration creates `subscription_plans`, `user_subscriptions`, `subscription_orders`, and `subscription_interests`. Legacy interests import once; PostgreSQL then owns interests, responses, deduplication, and usage. Existing legacy `premiumMember` flags do not grant access. Badge and visibility boosts follow active, unexpired subscription snapshots. Free members retain existing mutual connections when access expires.

Catalogue settings live in `server/.env.example`: integer paise prices, a configurable Free discovery limit (default 20), and an unset billing duration in days. Environment settings initialize missing plans only. Subsequent changes are persisted in the admin catalogue and audited; restarting never overwrites them. Existing paid memberships and pending orders retain their purchase snapshots. UTC calendar-month interest limits (5/50/unlimited) are independent of billing duration. Changing plans does not reset usage. Effective expiry is checked server-side on every authenticated request; no cron job or browser clock is trusted.

No payment provider exists in this project. Paid checkout and verification deliberately return 503; nothing can activate a paid plan from browser-supplied payment success, plan, price, expiry, or premium flags. Free requires no checkout. Current-plan management is at `/subscriptions` and on My Profile.

To enable payments, implement the `PaymentProvider` adapter in `src/services/subscriptionPayments.ts` using the chosen provider's authenticated server API. Configure the billing duration first. `createOrder` must use the local order ID as an idempotency key and return an HTTPS checkout URL. `verifyPayment` must retrieve captured status, provider order ID, amount, and currency directly from the provider. Wire the real provider return flow to authenticated `POST /api/subscriptions/verify` with order/payment references. The server checks ownership and all payment fields, locks the user/order, and activates access atomically. Repeated verification is idempotent. A unique payment ID prevents replay; one pending order per account prevents duplicate checkout. Add provider signature verification, webhook reconciliation, abandoned-order resolution and refund handling as required by the selected provider before enabling live purchases. No automatic renewals are implemented.

Endpoints: public `GET /api/subscriptions/plans`; authenticated `GET /me`, `POST /checkout` (`planId`), and `POST /verify` (`orderId`, `paymentId`) under `/api/subscriptions`. Admin accounts cannot purchase or activate member plans. Priority/dedicated support levels are stored as entitlements for the support workflow; no invented support contact or SLA is published.
